    Qué vas a construir

    Lee esto antes de tocar nada. Diez minutos.

    Un embudo completo de webinar en vivo: una página que registra, una que confirma, una puerta que abre sola quince minutos antes de la clase, una oferta que cobra, y un panel desde el que cambias fecha, enlaces y precio sin tocar código.

    La decisión que lo hace distinto: GoHighLevel es la única base de datos. No hay Supabase, no hay Postgres, no hay cron. Los prospectos son contactos de tu sub-cuenta. La configuración vive en los custom values de esa sub-cuenta. Los correos y WhatsApp los manda GHL con sus workflows. El sitio solo hace las páginas y captura.

    Antes de empezar
    01

    Tu taller: VS Code y Claude

    Cuarenta minutos, una sola vez. Después de esto todo se hace desde aquí.

    Qué es

    Vas a trabajar desde un solo lugar: Visual Studio Code con la extensión de Claude Code abierta a un lado. Claude es quien escribe el código, corre los comandos y publica; tú le pides. Para que pueda hacerlo, tu computadora tiene que estar conectada a tus cuentas de GitHub y de Vercel. Se conectan una vez, con tu navegador, y quedan guardadas.

    Hazlo

    A. Las herramientas base

    1. Visual Studio Code: descárgalo de code.visualstudio.com e instálalo.
    2. Node.js (versión 20 o más nueva): nodejs.org, la versión marcada LTS.
    3. Git: en Mac ya viene (abre la Terminal y escribe git --version; si pide instalar, acepta). En Windows, git-scm.com.

    B. Claude Code dentro de VS Code

    1. Abre VS Code. Extensiones (icono de cuadros a la izquierda, o Cmd+Shift+X / Ctrl+Shift+X), busca Claude Code (de Anthropic) e instálala.
    2. Aparece un icono de Claude en la barra lateral. Ábrelo: te pide iniciar sesión en el navegador con tu cuenta de Claude. Acepta y vuelve a VS Code.
    3. Instala también la versión de terminal, para que Claude pueda correr comandos. Abre la terminal de VS Code (Terminal → Nueva terminal) y pega: 
      # Mac
curl -fsSL https://claude.ai/install.sh | bash
# Windows (PowerShell)
irm https://claude.ai/install.ps1 | iex
      Cierra y vuelve a abrir la terminal, y comprueba con claude --version.

    C. Conectar GitHub

    1. Instala la herramienta de GitHub. Mac: brew install gh (si no tienes Homebrew, cli.github.com tiene el instalador). Windows: winget install GitHub.cli.
    2. Conéctala a tu cuenta. Se abre el navegador, entras a GitHub, aceptas: 
      gh auth login
      Elige GitHub.com, protocolo HTTPS, y Login with a web browser. Copia el código que te muestra y pégalo en el navegador.
    3. Comprueba: gh auth status debe decir Logged in to github.com.

    D. Conectar Vercel

    1. Instala la herramienta de Vercel: 
      npm install -g vercel
    2. Conéctala. Se abre el navegador; si tu cuenta tiene verificación en dos pasos, te pide el código de tu app de autenticación: 
      vercel login
    3. Comprueba: vercel whoami debe mostrar tu usuario.
    Por qué la terminal y no solo el chat

    El chat de Claude en VS Code sirve para pedirle cosas. Pero crear tu repositorio, subir variables o publicar son comandos de GitHub y de Vercel. Con las dos herramientas conectadas, Claude los corre por ti y tú solo apruebas.

    Si algo falla

    • "command not found: claude / gh / vercel". Cierra la terminal y ábrela de nuevo; los instaladores agregan la ruta al abrir una terminal nueva.
    • npm install -g pide permisos en Mac. No uses sudo. Reinstala Node desde nodejs.org, que deja los permisos bien.
    • Claude no abre el navegador para iniciar sesión. Copia la URL que muestra en la terminal y ábrela a mano.

    Tu copia, desde Claude Code

    Diez minutos. Al final tienes tu propio repositorio y el sitio corriendo en tu computadora.

    Qué es

    La plantilla es un repositorio de GitHub marcado como template. No la clonas: creas tu propia copia, que es tuya para siempre. Los cambios que hagas no tocan la plantilla, y las mejoras futuras de la plantilla no te llegan solas. Eso es a propósito: tu embudo no cambia sin que tú lo decidas.

    Hazlo

    1. En VS Code, Archivo → Abrir carpeta y elige la carpeta donde guardas tus proyectos (por ejemplo Documentos/proyectos).
    2. Abre la terminal (Terminal → Nueva terminal) y arranca Claude: 
      claude
    3. Pídele que cree tu copia. Cambia el nombre por el de tu webinar, en minúsculas y sin espacios:

    Claude va a correr, más o menos, esto (aprueba cada paso cuando te lo muestre):

    gh repo create webinar-mi-programa --template davidiriza-lab/plantilla-webinar-ghl --private --clone
cd webinar-mi-programa
npm install
cp .env.example .env.local
    1. Abre esa carpeta nueva en VS Code (Archivo → Abrir carpeta). A partir de aquí, Claude siempre se abre dentro de ella: el archivo CLAUDE.md le explica el proyecto.
    2. Comprueba que el sitio arranca: 
      npm run dev
      Abre http://localhost:3000. Verás la plantilla con el copy de ejemplo. Ciérralo con Ctrl+C.
    Pídele a ClaudeExplícame en tres líneas qué hace cada carpeta de src/ y dónde está el copy que voy a cambiar.

    Si algo falla

    • "repository not found" al crear la copia. Tu cuenta no tiene acceso a la plantilla. Pide el enlace de nuevo o que te agreguen.
    • npm install falla. Revisa node -v: necesitas 20 o más.
    Módulo 02
    03

    Conectar GoHighLevel

    Treinta minutos. El paso más importante del cuaderno.

    Qué es

    El sitio necesita dos cosas para hablar con tu sub-cuenta: una llave (el Private Integration Token) y la dirección (el Location ID). Con eso, el instalador crea en tu sub-cuenta todo lo que el embudo usa: los custom values donde vive la configuración, dos campos de contacto, y verifica el pipeline.

    Cómo funciona

    Un Private Integration Token es una llave que GHL le da a una integración, con permisos concretos. No caduca por tiempo: solo muere si alguien la borra desde la sub-cuenta. Por eso es la llave correcta para algo que va a vivir meses. Las "API keys" viejas de GHL ya no sirven para esto.

    El instalador (npm run instalar) es idempotente: puedes correrlo veinte veces y solo crea lo que falta. Nunca borra ni sobreescribe valores que ya existan.

    Hazlo

    A. La zona horaria de la sub-cuenta

    1. En GHL: Configuración → Perfil de la empresa → Zona horaria. Ponla en la de tu audiencia (por ejemplo America/Mexico_City).
    Trampa conocida

    Los workflows de GHL (recordatorios por correo y WhatsApp) usan la zona horaria de la sub-cuenta, no la del panel del sitio. Si la sub-cuenta está en Los Ángeles y tu clase es en Ciudad de México, los recordatorios salen dos horas tarde. El instalador te lo avisa.

    B. El token

    1. Configuración → Integraciones privadas → Crear nueva integración.
    2. Nombre: Embudo webinar. Permisos (scopes): marca Contacts (ver y editar), Opportunities (ver y editar), Locations con Custom Values y Custom Fields (ver y editar), y Tags si aparece aparte.
    3. Copia el token. Empieza con pit-. Solo se muestra una vez.

    C. El Location ID

    1. Configuración → Perfil de la empresa. Es una cadena de unos 20 caracteres. También aparece en la URL cuando estás dentro de la sub-cuenta: …/location/AQUÍ/….

    D. El pipeline, a mano

    La API oficial de GHL no crea pipelines, así que este es el único paso manual. Dos minutos:

    1. Oportunidades → Pipelines → Crear pipeline. Nombre: Webinars.
    2. Cuatro etapas, en este orden y con estos nombres: Nuevo Registro, Asistió al Webinar, Cliente Potencial, Cliente Ganado.

    El sitio las encuentra por nombre (sin distinguir acentos ni mayúsculas). No hay que copiar ningún ID.

    E. Llenar el archivo y correr el instalador

    1. Abre .env.local y llena GHL_API_KEY, GHL_LOCATION_ID y ADMIN_PASSWORD (la contraseña con la que entrarás a tu panel).
    2. Corre: 
      npm run instalar
      Vas a ver algo así: 
      1. GoHighLevel
  ✓ Sub-cuenta "Mi negocio" · zona horaria America/Mexico_City
2. Custom values (la configuración que edita /admin)
  + "Titulo del webinar"
  + "Webinar Modo"
  … (crea 29 la primera vez)
3. Custom fields de contacto (Fuente y Fecha de su clase)
  + campo "Fuente"
  · GHL_CAMPO_FUENTE_ID=xxxx → se escribe en .env.local
4. Pipeline de oportunidades
  ✓ Pipeline "Webinars" con sus 4 etapas
5. Panel /admin
  · ADMIN_SESSION_SECRET generado → se escribe en .env.local

Todo listo del lado de GoHighLevel.
    3. Si algo sale con ✗, el mensaje dice qué hacer. Corrígelo y vuelve a correrlo.

    Si algo falla

    • "El token no entra a la sub-cuenta (HTTP 401)". El token está mal copiado, o es de otra sub-cuenta. Los PIT son por sub-cuenta, no por agencia.
    • "No se pudieron leer los custom values (HTTP 403)". Le faltó un permiso al token. Edita la integración en GHL y agrega Custom Values y Custom Fields.
    • "No existe un pipeline llamado Webinars". Vuelve al paso D. Si lo llamaste distinto, pon el nombre en GHL_PIPELINE_NOMBRE en .env.local.
    Módulo 03
    04

    El panel de control

    Veinte minutos. Aquí vive todo lo que cambia de semana en semana.

    Qué es

    /admin es la única pantalla que vas a abrir cada semana. Desde ahí fijas el día y la hora de la clase, el enlace de Zoom, el grupo de WhatsApp, el precio, el enlace de pago y el pixel. Nada de eso está en el código: todo son custom values de tu sub-cuenta de GHL, los mismos que puedes usar en tus correos con {{custom_values.enlace_de_ingreso_al_webinar}}.

    Cómo funciona

    Cuando guardas en el panel, el sitio escribe en dos lugares: en GHL (la fuente de verdad) y en una copia en Vercel Edge Config (lo que leen las páginas). Las páginas nunca le preguntan a GHL en cada visita; leen la copia, que responde en milisegundos y no depende de que GHL esté vivo. Si editas un custom value directo en GHL, el panel lo detecta al abrirse y actualiza la copia.

    El panel muestra arriba un banner de salud. Si dice algo en rojo, es lo primero que hay que arreglar: "GoHighLevel no responde con el token actual", "Falta el enlace de pago", "La fecha única ya pasó". Si no dice nada, todo está bien.

    Hazlo

    1. Arranca el sitio y entra al panel con tu contraseña: 
      npm run dev
# abre http://localhost:3000/admin
    2. Recorre los grupos del panel y llena lo que ya tengas:
    GrupoQué decidesConsejo
    ProgramaciónModo recurrente (cada jueves) o fecha única; día, hora, zona, duraciónRecurrente si vas a dar la clase cada semana. Fecha única cierra el registro sola cuando pasa.
    La salaCuántos minutos antes abre la puerta; mando manual (auto / abierta / cerrada)15 minutos. Deja el mando en auto salvo el día de la clase si quieres abrir antes.
    EnlacesZoom, grupo de WhatsApp, WhatsApp de soporteEl Zoom con contraseña incluida en el enlace (?pwd=…), para que nadie tenga que teclearla.
    La ofertaPrecio (solo el número, en MXN), enlace de pagoSin enlace de pago el botón se ve, pero avisa que falta. Lo llenas en el módulo 08.
    EtiquetasLos nombres de las etiquetas generalesDéjalas como vienen. Son las que disparan tus workflows (módulo 06).
    SeguimientoPixel de Meta y token de conversionesMódulo 09. Puede quedar vacío hasta entonces.
    1. Guarda. Abre http://localhost:3000 en otra pestaña: la fecha y la hora ya son las tuyas.
    Regla

    Si quieres cambiar fecha, enlace, precio o pixel, es en el panel. Si le pides a Claude "cambia la fecha a…", te va a decir lo mismo. Está bien que lo haga: así nadie edita código para algo que cambia cada semana.

    Tu copy y tu marca

    Una o dos horas, según cuánto copy ya tengas. Aquí es donde Claude más ayuda.

    Qué es

    Todo el texto del sitio vive en tres archivos dentro de src/contenido/. Las páginas solo lo acomodan. Nunca vas a editar una página para cambiar una frase.

    ArchivoQué contiene
    marca.tsTu nombre, tu rol, el nombre del webinar y del producto, logo, retrato, dominio, SEO, aviso legal
    landing.tsTodo el copy de la página de registro y de la de gracias: hero, los 3 puntos, para quién es, casos, cierre
    oferta.tsLas nueve secciones de la oferta: problema, etapas, qué incluye, garantía, inversión, cierre

    Cómo funciona

    Cada texto de ejemplo lleva al final una marca // EJEMPLO. Cuando cambies el texto, borra la marca. El comando npm run revisar lista los que siguen marcados, con su número de línea. Cuando la lista quede vacía, la plantilla es tuya.

    Las imágenes van en public/assets/ y se referencian por ruta desde los archivos de contenido. Si una ruta queda vacía (''), el sitio muestra un marcador con la descripción de lo que falta. Las secciones con listas vacías (carrusel, casos de éxito) simplemente no se muestran. Así el sitio se ve terminado aunque todavía no tengas fotos.

    Los colores son nueve variables al principio de src/app/globals.css. Las tipografías, dos líneas en src/app/layout.tsx.

    Hazlo

    1. Empieza por marca.ts: nombre, rol, producto, dominio. Es corto y lo usa todo lo demás.
    2. Sigue con landing.ts. Si ya tienes el copy, pégalo. Si no, dictaselo a Claude por secciones:
    Pídele a ClaudeMi clase se llama "[nombre]". La doy para [audiencia] que tiene [problema]. Al final ofrezco [producto] a [precio]. Reescribe el hero, los 3 puntos y "para quién es" en src/contenido/landing.ts con mi voz, y borra las marcas EJEMPLO de lo que cambies.
    1. Luego oferta.ts. Si tu oferta no son cuatro etapas de 30 días, cámbialo: es una lista, puede tener tres o seis.
    2. Colores: pídele a Claude que ajuste las nueve variables a tu paleta, o dale tu color principal y que derive el resto.
    3. Revisa qué falta: 
      npm run revisar
    Copy de venta

    La plantilla trae una estructura probada, no tu argumento. Lo que convierte es tu problema concreto, tu promesa concreta y tu prueba. Cambia el sentido de las frases, no solo los nombres.

    06

    Etiquetas y automatizaciones

    Una hora en GHL. Es lo que hace que la gente llegue a la clase.

    Qué es

    El sitio no manda correos ni WhatsApp. Lo que hace es poner etiquetas en el contacto en cada momento del embudo, y tus workflows de GHL se disparan con esas etiquetas. Tú decides qué se manda y cuándo; el sitio solo avisa "esta persona acaba de registrarse".

    Cómo funciona

    Cada envío pone dos etiquetas: una general, fija, que dispara la automatización; y una con la fecha de la clase, para poder filtrar por edición. GHL guarda las etiquetas en minúsculas.

    / · registro
    Se registró
    registro webinarregistro 24-septiembre
    → Nuevo Registro
    /ingreso · puerta
    Entró a la sala
    ingreso webinaringreso 24-septiembre
    → Asistió al Webinar
    /oferta · comprar
    Fue a pagar
    carrito webinarcarrito 24-septiembre
    → Cliente Potencial
    webhook de pago
    Pagó
    pago webinarpago 24-septiembre
    → Cliente Ganado

    Además, cada contacto lleva dos campos: Fuente (de qué anuncio vino, armado con los parámetros UTM del enlace) y Fecha de su clase (el texto "jueves 24 de septiembre", para que tus correos lo digan sin calcular nada).

    Hazlo

    Crea en GHL, como mínimo, estos tres workflows. Cada uno se dispara con Contact Tag → Added → la etiqueta general.

    WorkflowDisparadorQué manda
    ConfirmaciónTag added: registro webinarCorreo inmediato: fecha, hora, enlace al grupo. Usa {{custom_values.webinar_proxima_fecha}} y {{custom_values.webinar_proxima_hora}}.
    RecordatoriosTag added: registro webinarEsperas hasta el día de la clase (usa el campo Fecha de su clase o una espera fija) y mandas: la mañana de la clase, 1 hora antes, 10 minutos antes con {{custom_values.enlace_de_ingreso_al_webinar}}.
    OfertaTag added: ingreso webinarDespués de la clase: la oferta, con {{custom_values.enlace_de_la_oferta}}. Opcional: una secuencia de 3 días.
    Dos trampas que cuestan una clase entera

    1. Activa "Allow Re-Entry" en cada workflow. Si alguien se registra a la clase de esta semana y ya se había registrado a la anterior, sin re-entrada no recibe nada. 2. Publica los workflows. Un workflow en borrador no manda nada, y GHL no avisa. Después de crearlos, haz un registro de prueba con tu correo y confirma que llega.

    Módulo 06
    07

    La puerta de la sala

    Diez minutos para entenderla. Es la pieza más delicada del sistema.

    Qué es

    /ingreso es la página a la que mandas a la gente para entrar a la clase. Antes de la hora muestra un contador. Quince minutos antes (o lo que pongas en el panel) se convierte en un formulario de nombre, correo y WhatsApp; al confirmarlo, la persona queda etiquetada como ingreso y se abre Zoom. Así sabes quién cruzó la puerta, no solo quién se registró.

    Cómo funciona

    La puerta está diseñada para equivocarse abriendo. Si el sitio no puede leer la configuración, abre. Si GHL no responde al momento de pasar lista, deja entrar igual y anota el fallo. Si alguien llega tarde, entra: la puerta se cierra al terminar la clase, no al empezar. La página no se cachea nunca y el navegador reevalúa cada segundo, así que quien la deje abierta ve cómo se habilita sola sin recargar.

    El enlace de Zoom nunca viaja al navegador antes de tiempo: el servidor también revisa la hora y responde "todavía no abre" aunque alguien cambie el reloj de su teléfono.

    El mando manual del panel gana sobre todo: abierta deja entrar desde ya (útil para abrir la sala antes con el contador visible), cerrada no deja entrar a nadie. Después de la clase, regresa el mando a auto; si lo dejas en abierta, la puerta nunca se cierra.

    Hazlo

    1. En el panel, pon el mando de la puerta en abierta y guarda.
    2. Abre /ingreso, llena tus datos y confirma: debe abrirse tu Zoom en otra pestaña.
    3. Revisa en GHL que tu contacto tiene ingreso webinar y está en Asistió al Webinar.
    4. Regresa el mando a auto y guarda. Abre /ingreso de nuevo: debe mostrar el contador.
    Módulo 07
    08

    La oferta y el pago

    Treinta minutos con Mercado Pago. Opcional si cobras por otro medio.

    Qué es

    /oferta presenta tu programa y manda a pagar. El cobro no lo hace el sitio: lo hace un enlace de pago (Mercado Pago, Stripe, Hotmart, el que uses) que pones en el panel. Lo que el sitio sí hace es saber quién fue a pagar y, si conectas el webhook de Mercado Pago, saber quién pagó.

    Cómo funciona

    Cuando alguien se registra o entra a la sala, el sitio guarda una cookie con su nombre, correo y teléfono (30 días). Si esa persona llega a la oferta desde el mismo navegador, el botón de comprar la manda directo al pago y la etiqueta como carrito en silencio. Si llega sin cookie (otro navegador, otro dispositivo), antes de pagar llena nombre, correo y WhatsApp. Nadie llega al cobro sin quedar en GHL.

    El webhook de pago (/api/pago/mercadopago) recibe el aviso de Mercado Pago, valida su firma, consulta el pago por su id (nunca confía en el aviso) y, si está aprobado: etiqueta pago webinar, mueve la oportunidad a Cliente Ganado con el monto, y manda un evento de compra a Meta. Es idempotente: si Mercado Pago repite el aviso, no duplica nada.

    Hazlo

    A. El enlace de pago (obligatorio para cobrar)

    1. Crea tu link de pago en tu pasarela. En Mercado Pago: Tu negocio → Link de pago, con el precio del programa.
    2. En el panel: grupo La oferta → precio (solo el número) y enlace de pago. Guarda.
    3. Abre /oferta en una ventana privada: debe pedirte datos y luego llevarte al link.

    B. El webhook (para ver ventas en el pipeline)

    1. Necesitas el sitio publicado (módulo 10) porque Mercado Pago tiene que alcanzar la URL.
    2. En Mercado Pago: Tus integraciones → Crear aplicación (si no tienes) → Producción → Credenciales. Copia el Access Token (APP_USR-…).
    3. En la misma app: Webhooks → Configurar notificaciones. URL: https://TU-DOMINIO/api/pago/mercadopago. Evento: Pagos. Al guardar, Mercado Pago genera una clave secreta: cópiala.
    4. En Vercel, agrega las variables MP_ACCESS_TOKEN y MP_WEBHOOK_SECRET y vuelve a desplegar.
    5. Haz un pago de prueba de monto mínimo (o con un cupón del 100% si tu pasarela lo permite) y revisa que el contacto llegue a Cliente Ganado.
    Si no conectas el webhook

    Todo lo demás funciona. Solo que Cliente Ganado se queda en cero y no sabrás qué anuncio vendió. Puedes cruzar a mano el reporte de tu pasarela con las etiquetas de carrito.

    Módulo 08
    09

    Meta: pixel y conversiones

    Veinte minutos. Opcional, pero sin esto tus anuncios no aprenden.

    Qué es

    El sitio manda a Meta tres eventos, cada uno una sola vez por persona: Lead cuando alguien se registra, Asistio (evento propio) cuando entra a la sala, y Purchase cuando paga. Con eso tu campaña optimiza hacia registros reales y puedes ver el costo por asistente y por venta.

    Cómo funciona

    Cada evento sale por dos caminos con el mismo identificador: el pixel del navegador y la API de conversiones desde el servidor. Meta los une y cuenta uno. El camino del servidor recupera lo que el navegador pierde por bloqueadores y por iOS. Por eso el Lead solo sale del registro: si la puerta también mandara Lead, Meta contaría a cada asistente como un registro nuevo.

    La fuente de cada contacto se arma con los parámetros UTM del enlace del anuncio. Si en Ads Manager usas utm_campaign={{campaign.name}}&utm_content={{ad.name}}, cada contacto en GHL dice de qué campaña y anuncio vino, sin que hagas nada.

    Hazlo

    1. En Meta Business: Administrador de eventos → tu pixel → Configuración → Generar token de acceso (API de conversiones).
    2. En el panel: grupo Seguimiento → id del pixel y el token. Guarda.
    3. Regístrate desde la landing y, en el Administrador de eventos, pestaña Probar eventos, confirma que llega un Lead "desde navegador y servidor".
    4. En tus anuncios, la URL de destino con UTMs: 
      https://TU-DOMINIO/?utm_source=fb&utm_medium=paid&utm_campaign={{campaign.name}}&utm_content={{ad.name}}
    Nombres de campaña

    Publicar en Vercel

    Treinta minutos la primera vez. Después, cada cambio se publica solo al subirlo a GitHub.

    Qué es

    Vercel es donde vive el sitio. Desde la terminal, con la cuenta que conectaste en el módulo 01, creas el proyecto, le subes las mismas variables que tienes en .env.local, y lo ligas a tu repositorio de GitHub: desde ese momento, cada vez que subes un cambio, Vercel lo publica. La copia en Edge Config es un almacén de Vercel donde el panel deja la configuración para que las páginas la lean sin depender de GHL; es lo único que se hace en el navegador.

    Hazlo

    A. Crear el proyecto y publicar la primera vez

    1. En la terminal, dentro de tu carpeta: 
      vercel link
      Responde: Set up → sí; Which scope → tu cuenta; Link to existing project → no; nombre → el de tu repo. Crea el proyecto y deja una carpeta .vercel (no se sube a GitHub).
    2. Sube tus variables. El comando lee .env.local y las manda todas: 
      npm run subir-env
    3. Publica: 
      vercel --prod
      Al terminar te da una URL .vercel.app. Ábrela y entra a /admin con tu contraseña.

    B. La copia (Edge Config), en el navegador

    1. En vercel.com, tu proyecto → pestaña Storage → Create Database → Edge Config. Nómbralo como tu proyecto y conéctalo a él: la variable EDGE_CONFIG se crea sola en Production y Preview.
    2. Copia el id que aparece (empieza con ecfg_) y ponlo en tu .env.local como EDGE_CONFIG_ID.
    3. Tu foto de perfil → Account Settings → Tokens → Create. Nombre: el de tu proyecto; alcance: tu cuenta. Copia el token a .env.local como VERCEL_API_TOKEN. Si tu cuenta es un equipo, pon también su id (Team Settings → General) en VERCEL_TEAM_ID; si es personal, déjalo vacío.
    4. Vuelve a subir las variables y a publicar: 
      npm run subir-env
vercel --prod
    5. Entra a /admin en tu URL y guarda una vez: eso siembra la copia. El banner de salud debe quedar sin avisos.

    C. Que cada cambio se publique solo

    1. Liga el proyecto a tu repositorio: 
      vercel git connect
      La primera vez te pide autorizar la app de Vercel en GitHub: acepta en el navegador. Desde ahora, cada git push a main publica.
    2. Prueba: cambia una frase en src/contenido/landing.ts y pídele a Claude que lo suba. En un par de minutos está en tu URL.

    El repositorio trae además un flujo de GitHub Actions que corre las pruebas en cada push (lo ves en la pestaña Actions). No necesita configuración: si una prueba falla, aparece en rojo y sabes que hay que revisar antes de seguir.

    D. Tu dominio

    1. Con el dominio ya comprado: 
      vercel domains add mi-dominio.com
      Te dice qué registro poner en tu proveedor (normalmente un A a 76.76.21.21 y un CNAME para www). Ponlos y espera a que Vercel lo marque válido (minutos, a veces horas).
    2. Actualiza sitio en src/contenido/marca.ts con tu dominio y súbelo.

    E. Comprueba la salud

    Abre https://TU-DOMINIO/api/salud. Debe decir "ok": true con cuatro revisiones en verde. Si un día algo se rompe, esta URL lo dice antes que nadie.

    Operar cada semana

    Quince minutos por semana. Esta es la rutina.

    Qué es

    Una vez publicado, el embudo se opera desde el panel y desde GHL. En modo recurrente, la fecha se recorre sola cuando termina cada clase: la landing, el calendario y las etiquetas pasan a la siguiente semana sin que hagas nada. Lo que sí cambia de semana en semana está aquí.

    La rutina

    Antes de la clase (el día anterior)

    • Abre /admin. Confirma fecha y hora. Revisa que el banner de salud esté limpio.
    • Si abriste un grupo de WhatsApp nuevo, cambia el enlace. Si el Zoom cambió, también.
    • Revisa en GHL cuántos contactos tienen registro <fecha>. Ese es tu número real de registrados a esta clase.
    • Toca Descargar respaldo en el panel y guarda el CSV. Es tu copia si alguien borra algo en GHL.

    El día de la clase

    • Si quieres abrir la sala antes de los 15 minutos, pon la puerta en abierta. El contador sigue visible.
    • Manda al grupo el enlace de /ingreso, no el de Zoom: así pasas lista.
    • Al soltar la oferta, manda el enlace de /oferta.

    Después de la clase

    • Regresa la puerta a auto.
    • Cuenta: registrados (registro <fecha>), asistentes (ingreso <fecha>), carritos (carrito <fecha>), pagos (pago <fecha>). Esa es tu conversión por etapa.
    • Si la próxima semana no hay clase, cambia a modo fecha única con la siguiente fecha; cuando reanudes, vuelve a recurrente.

    Trabajar con Claude Code

    Cómo pedirle cosas para que las haga bien la primera vez.

    Qué sabe

    El archivo CLAUDE.md del proyecto le dice a Claude dónde vive cada cosa, qué reglas sigue el proyecto y qué comandos correr. Por eso puedes pedirle cambios sin explicarle la arquitectura. Y por eso, si le pides algo que rompe una regla (poner una fecha en el código, mandar Lead desde la puerta), te lo va a decir.

    Lo que le pides bien

    CopyReescribe la sección "para quién es" de landing.ts para una audiencia de [quién], con [tono]. Borra las marcas EJEMPLO.
    DiseñoCambia la paleta en globals.css a partir de este color principal: #7c2d12. Mantén el contraste de los botones.
    Una sección nuevaAgrega en la landing, antes del cierre, una sección de preguntas frecuentes con 5 preguntas. El copy va en landing.ts, no en la página.
    Antes de publicarCorre npm run verificar y dime si algo falla.
    Un problemaMe registré y no apareció la oportunidad en el pipeline. Esto dice /api/salud: [pega]. ¿Qué reviso?

    Lo que no le pidas

    • Cambiar fecha, hora, enlaces, precio o pixel editando código. Eso es el panel.
    • "Agrega Supabase para guardar los registros". GHL ya los guarda; una segunda base es una segunda cosa que mantener.
    • Meter un contador de urgencia falso en la oferta. Puede hacerlo, pero la plantilla no lo trae por una razón.

    El ciclo de trabajo

    1. Pides el cambio en Claude Code.
    2. Lo ves en npm run dev.
    3. npm run verificar.
    4. Le pides a Claude "súbelo": hace commit y push, y Vercel lo publica.
